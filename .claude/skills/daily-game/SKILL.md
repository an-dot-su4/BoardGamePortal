# 毎日の試作ゲーム

ユーザーは毎日は確認できない。だから自動で作ったゲームはメインのポータルに出さず、
`trial: true` を付けて試作ページ（`lab.html`）にだけ並べる。メインへの昇格はユーザーの OK のあと（`promote-game` スキル）。

## 0. 準備

1. `TZ=Asia/Tokyo date '+%Y-%m-%d'` で今日（JST）の日付を決める。以下 `YYYY-MM-DD`。
2. `git fetch origin main` して、main の最新から作業ブランチを作る（main へ直接 push しない）。
3. `games/registry.js` に `addedAt: 'YYYY-MM-DD'` のゲームがすでにあれば、今日の分は作成済み。何もせず「作成済み」とだけ報告して終わる。

## 1. 何を作るか決める

- `games/registry.js`（メイン＋試作の全部）と `docs/daily-game-ideas.md`（これまでの案・採用・却下の記録）を読む。
- **既存と遊びの中心が被らない**ものを1つ選ぶ。ジャンルが偏らないよう、直近の試作と違う系統を優先する
  （例: トランプの定番遊び、伝統的な盤ゲーム、言葉・連想、推理、陣取り、競り、ブラフ、早押し・リアルタイム、協力、2人専用 など）。
- 却下された案（とその理由）は繰り返さない。理由が「難しすぎる」などなら、その反省を今日の案に生かす。
- 市販ゲームの名前・アート・固有のテキストは使わない（CLAUDE.md の「注意」）。定番の伝統遊び・トランプ遊び、または着想を得たオリジナルにする。
- 1回で仕上げて確認まで終えられる規模にする。凝りすぎるより、ルールが明快で最後まで遊べることを優先する。
  CPU（`bot`）があると1人でも確認しやすいので、できるだけ付ける。

## 2. 作る・確かめる

`.claude/skills/add-game/SKILL.md` の「2. 作る」「3. 確かめる」に従う。違いは次のとおり:

- `games/registry.js` には配列の**末尾**に、`trial: true, addedAt: 'YYYY-MM-DD'` を付けて追加する。
- README の「収録ゲーム」表には**まだ書かない**（昇格のときに書く）。
- `tests/e2e-games.mjs` の `scenarios` にシナリオを足す（`openGame` は試作ゲームなら自動で lab.html から部屋を作る）。
- `npm test`、`SHOTS=<dir> node tests/e2e-games.mjs <id>`、`MOBILE=1` 付きでも通し、スクリーンショットを**必ず目で見て**崩れがないか確認する。
- どうしても通らない・遊べる状態にならない場合は main に入れない（ブランチだけ push して、失敗として報告する）。

## 3. 記録する

`docs/daily-game-ideas.md` の表に1行足す: `| YYYY-MM-DD | <id> | <名前> | <一言説明> | 試作 |`

## 4. 公開する

1. commit（メッセージ例: `試作ゲーム「<名前>」を追加`）→ 作業ブランチに push。
2. PR を作る（base: main、タイトル: `試作ゲーム: <名前>（YYYY-MM-DD）`、本文にルール要約と決めた点）。
3. PR の CI（テスト）が緑になるのを確認してから、**この実行で自分が作ったこの PR だけを** merge する（merge_method: merge）。
   試作ページにしか出ないので、ユーザーの確認前に main に入れてよい（ユーザーがそう決めている）。CI が赤なら直してから。
4. main の Actions（GitHub Pages への公開）が成功したことを確認する。

## 5. 報告（日本語で短く）

- ゲーム名・人数・対戦/協力・CPU の有無
- 遊び方の要約（3〜5行）とこちらで決めた点
- 試作ページ: https://an-dot-su4.github.io/BoardGamePortal/lab.html
- 「よければ『<名前>をOK』、だめなら『<名前>はNG（理由）』と Claude に伝えてください」
